# FlagGems AMD Instinct MI355X (gfx950) 性能测试报告

> 方法与算子清单对齐 `testing_notes/FlagOS/FlagGems/R9700_FLAGGEEM_RESULTS.md`
> 与 `MI300X_FLAGGEMS_RESULTS.md`，以便与 gfx1201 (RDNA4)、gfx942 (CDNA3) 的结果直接比较。

## 1. 结论摘要

- 测试 10 类算子、FP16/BF16、5 个官方 core shape，共 100 个 shape/dtype 用例，全部成功产出数据，无失败或跳过。
- Kernel 模式：46 个加速超过 2%，12 个近似持平，42 个慢超过 2%。
- Operator 模式：7 个加速超过 2%，3 个近似持平，90 个慢超过 2%。
- 46 个 Kernel 加速用例中，只有 6 个在真实调用中保留收益，40 个被派发/启动开销抵消。
- 唯一稳定值得保留的是大规模 Softmax 与最大规模 LayerNorm，与 MI300X、R9700 的结论方向一致。
- MM/BMM 在两种模式下均无收益；`mm [[4096,4096]]` 仅 0.55x，是全部用例中退化最严重的一类。
- FlagGems 在 operator 模式的延迟存在约 0.012–0.032 ms 的固定地板（中位 0.023 ms），
  在 gfx950 这种高算力卡上足以吞掉多数算子的 kernel 收益。

## 3. 与 MI300X (gfx942)、R9700 (gfx1201) 的对比

| 指标 | R9700 gfx1201 (64 CU) | MI300X gfx942 (304 CU) | MI355X gfx950 (256 CU) |
|---|---|---|---|
| Kernel 加速 / 持平 / 退化 | 39 / 30 / 31 | 47 / 17 / 36 | 46 / 12 / 42 |
| Operator 加速 / 持平 / 退化 | 15 / 24 / 61 | 6 / 1 / 93 | 7 / 3 / 90 |
| Kernel 收益在真实调用中存活 | 12 / 39 | 6 / 47 | 6 / 46 |
| Operator 模式 FlagGems 延迟地板 | — | 0.022–0.044 ms | 0.012–0.032 ms |

gfx950 与 gfx942 的画像高度接近（46/12/42 对 47/17/36，存活 6 对 6，且是同一组算子与 shape），
说明**这套结论由 CDNA 架构的高算力特征决定，而非某一代芯片的个案**：
基线 PyTorch kernel 本身已被压到微秒级，FlagGems 的固定派发开销占比因此极高。
gfx950 的延迟地板比 MI300X 低约三分之一，但基线也更快，两者相抵，存活率没有改善。

相比之下 R9700 (64 CU) 存活率明显更高（12/39），因为算力较低时基线 kernel 本身耗时更长，
固定开销占比小，Triton kernel 的优化更容易兑现到真实调用。

## 4. 测试命令

```bash
cd /target/FlagGems
unset HIP_VISIBLE_DEVICES CUDA_VISIBLE_DEVICES TRITON_PRINT_AUTOTUNING
export GEMS_VENDOR=amd
export ROCR_VISIBLE_DEVICES=0

BENCHMARKS=(
  benchmark/test_mm.py::test_mm
  benchmark/test_bmm.py::test_bmm
  benchmark/test_softmax.py::test_softmax
  benchmark/test_sum.py::test_sum
  benchmark/test_mean.py::test_mean
  benchmark/test_mul.py::test_mul
  benchmark/test_sub.py::test_sub
  benchmark/test_div.py::test_div
  benchmark/test_layer_norm.py::test_layer_norm
  benchmark/test_rms_norm.py::test_rms_norm
)

# 每种模式：先预热一轮，再正式记录三轮
for mode in kernel operator; do
  python -m pytest "${BENCHMARKS[@]}" -s --level core --mode $mode \
    --dtypes float16 --dtypes bfloat16 --warmup 1000 --iter 100
  for r in 1 2 3; do
    python -m pytest "${BENCHMARKS[@]}" -s --level core --mode $mode \
      --dtypes float16 --dtypes bfloat16 --warmup 1000 --iter 500 \
      --record json --output "run_results/benchmark/gpu0/${mode}_run$r.json"
  done
done
```

`--warmup 1000 --iter 500` 是毫秒预算，不是固定调用次数。
单轮 kernel 模式约 3m15s，单轮 operator 模式约 2m21s。

## 9. 说明与限制

- speedup = PyTorch 延迟 / FlagGems 延迟，大于 1.0x 表示 FlagGems 更快。
- 分类：`>1.02x` 加速，`0.98–1.02x` 近似持平，`<0.98x` 退化。
- 每种模式先预热，再正式运行三轮；逐『算子 + dtype + case 序号』取三轮中位数。
- Kernel 模式经 `triton.testing.do_bench(..., return_mode="median")`，主要反映 GPU 稳态时间。
- Operator 模式为同步前后墙钟，含 Python、ATen/FlagGems 派发与 kernel launch。
- 两种模式计时机制不同，绝对延迟不应跨模式相减，应各自与 PyTorch 比较。
- `mm` 的官方 core shapes 中 `[[4096,4096],[4096,4096]]` 出现两次（case 1 与 case 4），
  按用例序号分别统计，与参考报告口径一致。
- AMD 后端无 gfx950 专属算子实现与调优配置，结论仅适用于未调优状态。
  仓库另有 `dev/amd-rdna4-*`、`amd-cdna3-split-softmax` 等针对其他架构的调优分支，本次未测。
- 结论只适用于当前 commit 与 ROCm/PyTorch/Triton 版本组合。

## 10. 复现性

**本报告未做 MI300X 报告中的独立二次复现（跑两整遍）**，仅有单遍内的三轮记录。
因此稳定性指标口径与 MI300X 报告不同，不可直接与其 0.63% / 0.89% 对比。

| 指标 | kernel 模式 | operator 模式 |
|---|---|---|
| 三轮内 speedup 相对波动（中位） | 1.23% | 1.54% |
| 波动 ≤5% 的用例 | 98/100 | 83/100 |

- Kernel 模式高度稳定：98/100 用例三轮波动在 5% 以内。
- Operator 模式波动更大（83/100），集中在微秒级的小 shape 用例上，
  与 MI300X 报告观察到的现象一致：总耗时仅数十微秒时，PyTorch 自身派发路径的抖动即可显著改变比值。

> 推论：kernel 模式的数字可直接引用；operator 模式在微秒级用例上应视为趋势而非精确值，
> 结论应建立在数量级差异（如 0.2x 与 2.0x）而非阈值附近的小数差别之上。

## 11. 正确性验证

安装后执行过快速正确性门禁：

```bash
python -m pytest tests/test_mm.py tests/test_bmm.py tests/test_softmax.py tests/test_sum.py \
  --quick --ref cpu -q --record json --output run_results/accuracy/core_quick.json
```

结果 36 passed / 1 skipped / 3 failed。3 个失败全部是 `test_bmm_w8a8_fp8`，
报错为 `assert ref.device == torch.device("cpu")`——该用例在 `--ref cpu` 模式下
自己在 GPU 上构造参考值，触发框架断言，属测试用例与 `--ref cpu` 模式不兼容。
去掉 `--ref cpu` 后 3 个用例全部通过，与 gfx950 无关，非精度问题。

## 12. 安装命令

```bash
cd /target
git clone -b master https://github.com/WhatGhost/FlagGems.git
cd FlagGems

# 安装主包与测试依赖（AMD 环境不执行 setup.sh，也不安装 C++ 扩展）

```

安装不触及 torch / triton / numpy / scipy。会按 FlagGems 的硬 pin 降级两个包：
