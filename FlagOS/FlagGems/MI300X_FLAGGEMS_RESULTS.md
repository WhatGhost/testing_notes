# FlagGems AMD Instinct MI300X 性能测试报告

> 方法与算子清单对齐 `testing_notes/FlagOS/FlagGems/R9700_FLAGGEEM_RESULTS.md`，
> 以便与 gfx1201 (RDNA4) 的结果直接比较。

## 1. 结论摘要

- 测试 10 类算子、FP16/BF16、5 个官方 core shape，共 100 个 shape/dtype 用例。
- Kernel 模式：47 个加速超过 2%，17 个近似持平，36 个慢超过 2%。
- Operator 模式：6 个加速超过 2%，1 个近似持平，93 个慢超过 2%。
- 47 个 Kernel 加速用例中，只有 6 个在真实调用中保留收益，41 个被派发/启动开销抵消。
- 唯一稳定值得保留的是大规模 Softmax 与最大规模 LayerNorm。
- MM/BMM 在 kernel 与 operator 两种模式下均无收益。
- FlagGems 在 operator 模式的延迟存在约 0.02–0.04 ms 的固定地板，在 MI300X 这种高算力卡上足以吞掉多数算子的 kernel 收益。

## 3. 与 R9700 (gfx1201) 的对比

| 指标 | R9700 gfx1201 (64 CU) | MI300X gfx942 (304 CU) |
|---|---|---|
| Kernel 加速 / 持平 / 退化 | 39 / 30 / 31 | 47 / 17 / 36 |
| Operator 加速 / 持平 / 退化 | 15 / 24 / 61 | 6 / 1 / 93 |
| Kernel 收益在真实调用中存活 | 12 / 39 | 6 / 47 |

MI300X 的 kernel 加速用例更多（算力更强，Triton kernel 更容易吃满带宽），
但真实调用存活率反而更低：基线 PyTorch kernel 本身已被压到微秒级，
FlagGems 的固定派发开销占比因此更高。

## 4. 测试命令

```bash
cd /target/FlagGems
unset HIP_VISIBLE_DEVICES CUDA_VISIBLE_DEVICES TRITON_PRINT_AUTOTUNING
export GEMS_VENDOR=amd
export ROCR_VISIBLE_DEVICES=0

BENCHMARKS=(
  benchmark/test_mm.py::test_mm
  benchmark/test_bmm.py::test_bmm
  benchmark/test_softmax.py::test_softmax
  benchmark/test_sum.py::test_sum
  benchmark/test_mean.py::test_mean
  benchmark/test_mul.py::test_mul
  benchmark/test_sub.py::test_sub
  benchmark/test_div.py::test_div
  benchmark/test_layer_norm.py::test_layer_norm
  benchmark/test_rms_norm.py::test_rms_norm
)

# 每种模式：先预热一轮，再正式记录三轮
for mode in kernel operator; do
  python -m pytest "${BENCHMARKS[@]}" -s --level core --mode $mode \
    --dtypes float16 --dtypes bfloat16 --warmup 1000 --iter 100
  for r in 1 2 3; do
    python -m pytest "${BENCHMARKS[@]}" -s --level core --mode $mode \
      --dtypes float16 --dtypes bfloat16 --warmup 1000 --iter 500 \
      --record json --output "json/${mode}_run$r.json"
  done
done
```

`--warmup 1000 --iter 500` 是毫秒预算，不是固定调用次数。

## 9. 说明与限制

- speedup = PyTorch 延迟 / FlagGems 延迟，大于 1.0× 表示 FlagGems 更快。
- 分类：`>1.02×` 加速，`0.98–1.02×` 近似持平，`<0.98×` 退化。
- 每种模式先预热，再正式运行三轮；逐『算子 + dtype + shape』取三轮中位数。
- Kernel 模式经 `triton.testing.do_bench(..., return_mode="median")`，主要反映 GPU 稳态时间。
- Operator 模式为同步前后墙钟，含 Python、ATen/FlagGems 派发与 kernel launch。
- 两种模式计时机制不同，绝对延迟不应跨模式相减，应各自与 PyTorch 比较。
- `mm` 的官方 core shapes 中 `[[4096,4096],[4096,4096]]` 出现两次，按用例序号分别统计，与参考报告口径一致。
- AMD 后端无 gfx942 专属算子实现与调优配置，结论仅适用于未调优状态。
- 结论只适用于当前 commit 与 ROCm/PyTorch/Triton 版本组合。

## 10. 复现性验证

为确认数据可靠，整套流程被独立执行了两遍（每遍各含预热与三轮记录）：
复现 A 在 `json/`，复现 B 在 `json2/`，同一张 GPU、同一 JIT 缓存。

| 指标 | kernel 模式 | operator 模式 |
|---|---|---|
| 两次复现 speedup 相对偏差（中位） | 0.63% | 0.89% |
| 相对偏差（最大） | 4.71% | 44.26% |
| 偏差 ≤5% 的用例 | 100/100 | 96/100 |

- Kernel 模式高度可复现：中位偏差不足 1%，全部 100 个用例偏差都在 5% 以内；
  分类计数 47/17/36 与 48/17/35 仅差 2 例，且这 2 例都是 `mul` 卡在 1.02 阈值边缘。
- Operator 模式整体也稳定（96/100 偏差 ≤5%），但存在单个 44% 的离群值：
  `mm float16 [[384,384],[384,384]]`。追查发现 FlagGems 侧在 6 轮中始终为
  0.0381–0.0405 ms，波动全部来自 PyTorch 基线（0.0266–0.0389 ms）——该用例总耗时
  仅 27–39 µs，PyTorch 自身派发路径的进程间抖动即可让比值在 0.67×–0.98× 间摆动。
- 最关键的结论完全一致：两次复现都是 **6 个** kernel 收益存活，
  且为同一组算子与 shape（大规模 Softmax ×4、最大规模 LayerNorm ×2），
  speedup 数值互差约 1%。

> 推论：kernel 模式的数字可直接引用；operator 模式在微秒级用例上应视为趋势而非精确值，
> 结论应建立在数量级差异（如 0.2× 与 2.0×）而非阈值附近的小数差别之上。
